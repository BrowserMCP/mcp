# Hidden-tab spike (#33, phase 0b)

Where AI agents' tabs live in the user's real Chrome.

**Setup.** Google Chrome 155.0.8059.85, macOS (Darwin 27), M1 Max with a 120 Hz display. Each run launches the real Chrome binary with a fresh temp `--user-data-dir`, `--remote-debugging-port=0`, and none of Playwright's automation or anti-throttling flags. Only `--no-first-run`, `--no-default-browser-check`, `--use-mock-keychain`, `--password-store=basic` and the window position/size are passed. On macOS it is started with `open -g -n` so it doesn't come to the front. The daemon connects with `chromium.connectOverCDP(..., { noDefaults: true })` from playwright-core 1.64.1 (see "Playwright's defaults" below). Fixture pages are served on `127.0.0.1:<random>`. Every operation has a 3 s timeout. The case's tab is the one the agent drives.

### Timers in a tab hidden for a long time (`long-hidden.ts`)

A chained `setTimeout(50)` fired 30 times per 30 s (once a second) for the first minute. **From about 1 minute** (not 5) it fired at most once a minute: 0 or 1 fire per 30 s window, through 6.5 min. A background tab that had focus emulation from the start kept firing ~550 times per 30 s the whole time. Turning focus emulation on after 6.5 min restored 57 ms timers and 115 rAF/s straight away, and every operation passed.

### Side effects (`side-effects.ts`, `focus-steal.ts`)

- **`Page.bringToFront`** (≈ `chrome.tabs.update({active:true})` plus focusing the window):
  - It works. The agent's tab is visible within 1–10 ms and its first rAF comes within 13–21 ms. A click takes 16–42 ms and a screenshot 32–44 ms. Switching back takes 6–9 ms, and the user's tab is visible again within 2–3 ms.
  - But the user's tab is hidden for **78–158 ms per step**, and **it activates Chrome, taking focus from the app the user is in**. Switching back activates it too. Measured: frontmost app before = the user's app, after = our Chrome.
- **Opening a background tab, an unfocused window, and turning on focus emulation** don't change the frontmost app. Focus emulation on 3 background tabs leaves the user's active tab `visible` with `hasFocus()` true.
- **Focus emulation ends** within 1–30 ms when it's turned off, or when the CDP session that turned it on detaches (so `chrome.debugger.detach` ends it).
- **Phantom input:** a raw `Input.dispatchMouseEvent` sent to a hidden tab isn't dropped. It hangs (`mouseMoved` 2.5 s, cut off), and the **click is delivered later, when the tab becomes visible** (clicks 0 → 1 after turning on emulation). Playwright's `click` times out before it dispatches anything, so it doesn't cause late clicks.
- **Screenshots in hidden tabs** return quickly and look successful, but show a blank page or a stale frame. Taking one also forces a frame, which applies queued scrolls, so it isn't a fix.
- **Playwright's defaults:** `connectOverCDP` without `noDefaults: true` enables `Emulation.setFocusEmulationEnabled` on every page in the default context. That's why a first probe saw background tabs "visible". Playwright MCP's extension mode passes `noDefaults: true`.
- **Headless** (`--headless=new`) hides background tabs just like headed Chrome (rAF 0, 1 s timers, click times out), so background-tab tests can run headless. Covered and minimized windows depend on the OS's occlusion tracking and need headed Chrome.

## Decision

**Agents' tabs stay background tabs in the user's window, as planned in decision 5, and the daemon turns on `Emulation.setFocusEmulationEnabled({enabled:true})` on every tab it attaches to.**

- **Focus emulation is the only page-level CDP command that helps, and it fixes everything.** In background tabs, covered windows, minimized windows and tabs hidden for minutes, the tab becomes `visible`. rAF, IntersectionObserver, lazy images, scroll events, timers, Playwright's actionability checks, input and screenshots all behave as in a foreground tab. It's reachable through `chrome.debugger` (Emulation is a page domain), takes effect within a millisecond, and doesn't steal focus or affect the user's tabs. It ends with the debugger session. `Page.setWebLifecycleState` and a running screencast change nothing.
- **A window of the agents' own doesn't help.** It renders only while nothing covers it. As soon as the user goes back to a maximized Chrome window, or another app's window covers it (the usual case), it's hidden like a background tab. It also puts a window in front of the user when it opens: a background app's new windows were ordered above the user's windows here. With focus emulation, it gives nothing a background tab doesn't already have.
- **Bringing a tab forward is ruled out.** It hides the user's tab for ~100 ms per step and activates Chrome over whatever app the user is in, on every switch.

## Guidance

### (a) Extension (phase 1b)

- `createTab`: `chrome.tabs.create({ url, active: false, windowId })` in the user's last focused normal window, then add it to the AI app's group. Don't create windows, and never pass `active: true`.
  - If there is no normal window, create one with `chrome.windows.create({ focused: false, state: "minimized" })`. Minimized works with focus emulation.
  - Keep moving popup windows into a normal window (section 2) as an inactive tab.
- `activateTab` is only for an explicit user action, such as clicking a tab in the popup. The daemon never calls it to make a page render.
- Time out every `Input.*` command, for example after 5 s. A hung `Input.dispatchMouseEvent` blocks the tab's serialized `Input.*` queue, and its event is delivered later when the tab becomes visible. On a timeout, fail the batch and report the tab's `visibilityState`. Don't retry blind.
- Detaching ends focus emulation, so nothing needs to be cleaned up on release. Emulation set in a Playwright child session ends when that child session detaches, so send it on the tab's root session (the `chrome.debugger` attachment), which lives as long as the attachment.

### (b) Command engine (daemon)

- **On claim** (the first command to a tab, right after attach): send `Emulation.setFocusEmulationEnabled({enabled:true})`, then wait for `document.visibilityState === "visible"`. It took under 10 ms here.
  - Connect Playwright with `noDefaults: true` and apply this one override explicitly, rather than taking Playwright's whole set of defaults on the user's tabs.
  - Pages see `document.hasFocus() === true` and get `focus` events. That's acceptable for tabs agents use.
  - Each emulated tab renders at full frame rate while attached. CPU cost wasn't measured. Lazy attach plus releasing after 10 idle minutes (decision 6) bounds it. Don't toggle emulation per step: off, timers throttle within a second and to once a minute after about 1 minute.
- **Before each action, check visibility.** Read `document.visibilityState` with `Runtime.evaluate`, which works in hidden tabs. If it's `hidden` (emulation lost, for example another client reset it), re-apply emulation and re-check. Never send `Input.*` to a hidden tab, because it hangs and fires later.
- **Actionability:**
  - With emulation on, Playwright's `click`, `fill`, `hover`, `wheel` and `scrollIntoViewIfNeeded` work. Keep them as the primary path.
  - The planned fallback ("our own scroll, hit-test and mouse input") **does not work in a hidden tab**: raw `Input.dispatchMouseEvent` and `mouse.wheel` hang too. Only JS-level actions run there (`Runtime.evaluate`, `fill`, `ariaSnapshot`). Keep the fallback for real actionability failures (animations, overlays), not for hidden tabs. If a tab can't be made visible, fail with a clear error rather than dispatching input.
- **Screenshots:** take them only once the tab is visible under emulation. Then `page.screenshot()` / `Page.captureScreenshot` takes 20–80 ms. A screenshot of a hidden tab returns quickly but is blank or stale, so it must never be returned to the model.
- **Lazy loading and infinite scroll:** with emulation, IntersectionObserver, `loading=lazy` and scroll-event loaders work as in a foreground tab. After scrolling, let a couple of frames pass (two rAFs) and settle briefly (network idle, or ~300–500 ms) before the snapshot, as for a visible tab.
- **Timers:** pages that poll with timers run normally under emulation. Without it, they stall to once a minute after about 1 minute hidden. So "waits" (`wait --text`, settling) on unclaimed tabs would be unreliable. Another reason to emulate on claim.

## Caveats

- Measured only on macOS (Chrome 155). Windows has its own occlusion tracking: covered windows should behave as on macOS, to check in 1b's end-to-end runs. Linux/X11 has none, so covered windows stay visible there. Background and minimized tabs are hidden on every OS.
- Covered-window occlusion is reported 1–3 s after the window is covered, and only when it's fully covered.
- `chrome.tabs.update({active:true})` from an extension wasn't measured separately from `Page.bringToFront`. Either way it switches the user's visible tab.
- **Windows on screen during the spike:** small Chrome windows (about 500×400) appeared in the lower-left corner of the main display (x 0–640, y 480–980), above the user's windows. That happened for every run (~40 launches, a few seconds each), for the two long runs (6.5 min and 5.5 min), and for the vitest suite. Launching a separate Chrome instance sometimes changed the frontmost app, even with `open -g`. `focus-steal.ts` re-activates the app that was frontmost before it ran. All instances were closed by PID. One instance that survived an early probe was found and killed by its PID.

## Files

- `lib.ts`: launching Chrome without flags, the fixture page and server, the operations and the timings.
- `measure.ts`: the case × mitigation matrix. `node measure.ts [cases] [--mitigations=…] [--headless] [--json=out.json]`, with `SHOT_DIR=…` to save screenshots.
- `long-hidden.ts`: the tab hidden for 6.5 minutes.
- `side-effects.ts`: bring-to-front costs, phantom input, focus emulation vs the user's tab, detaching.
- `focus-steal.ts`: which operations take focus from the user's app (macOS).
- `probe.ts`, `covered-probe.ts`, `windows.jxa.js`: quick probes (headed vs headless, occlusion, window z-order).
- `hidden-tabs.test.ts`: the cases as Vitest tests in headed Chrome, skipped unless `BROWSER_MCP_HEADED_TESTS=1`. `BROWSER_MCP_HIDDEN_MINUTES` shortens the 5.5 minute case. All 11 pass (about 7 minutes).
